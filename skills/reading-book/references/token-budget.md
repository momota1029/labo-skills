# 長い教材の消費予算

長い教材（数百〜数万頁）を、統括と worker の組で制作・確認するときの規則。
1 頁あたりの消費を一定に保ち、文脈を育てないことが目的である。正しさの基準や確認の要否は変えない。

## 何が消費を決めるか

モデルを呼ぶたびに、それまでの文脈全体が読み直される。消費はおおよそ「呼出回数 × その時点の文脈の大きさ」の総和で、
出力した量よりこちらが大きい。特に、一度読み込んだ頁画像やファイル全体は、その後の全ての呼出で読み直される。
したがって、文脈を大きくした agent に細かい操作を何百回もさせる形が最も高くつく。

## 規則

1. **一 worker 一単位。** worker は一節・一構成・一証明など一つの単位だけを担当し、呼出回数と文脈に上限を置く
   （目安：ツール呼出 30 回、文脈 8 万トークン）。超えそうなら途中結果と残りを返して終える。統括は新しい worker に
   続きを渡し、同じ worker を何単位も使い回さない。
2. **packet だけを渡す。** 対象行、引用ラベルの主張（証明は除く）、原著の該当頁の文字、hash を
   [make_packet.py](../scripts/make_packet.py) で切り出して渡す。章ファイル全体、進捗の全文、他の報告は読ませない。
3. **原著は文字で読む。** 原著は一度だけ [source_text_cache.py](../scripts/source_text_cache.py) で頁ごとの文字にし、
   キャッシュを全ての Git の外に置く。頁画像は、式・量化子・添字が文字では判読できない頁だけ、一単位で数頁まで。
4. **統括は状態だけを見る。** 統括は大きなファイルを読まず、短い状態要約（教材ごとのスクリプト等）と worker の
   短い返却だけで回す。シェル操作はまとめ、出力を短くする。文脈が育ったら状態を書いて新しい文脈から再開する。
5. **確認は差分とリスクで選ぶ。** 数学確認の重点は [math review の段階](../../reading-book-math-review/SKILL.md#重点の段階)、
   出力確認は [機械検査先行](../../reading-book-output-review/SKILL.md#機械検査を先に) に従う。
6. **機械でできることはスクリプト。** 状態集計、hash、存在確認、packet 作成、出力検査、公式ビルドは LLM に読ませない。
7. **役割カード。** worker には、担当スキルの要点を一枚にした役割カードと packet だけを渡し、スキルの参照連鎖を
   毎回読ませない。カードは教材ごとに作り、規則の正本は各スキルに残す。
8. **重いモデルは新しい証明に。** 上位モデルは、新しい証明の作成とその独立確認に充て、数単位分をまとめて渡す。
   原著の議論の転記・照合・出力確認には通常のモデルを使う（実際の選択はホスト設定に従う）。

消費の原因を調べるときは、ホストのセッション記録から役割別・モデル別に呼出回数と文脈の大きさを集計し、
画像の読込回数を数える。推測で規則を足さない。
