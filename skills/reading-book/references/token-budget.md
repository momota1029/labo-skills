# 規模と確認の水準・消費予算

教材や文書を、統括と worker の組で制作・確認するときの規則。正しさの基準は変えず、
**対象の規模に応じて確認の深さと消費の配分を選ぶ**。

## 規模の判定

判定は頁数ではなく、**一つの確認担当が一回の文脈で対象全体（本文と直接の前提）を読み通せるか**で行う。
頁数は目安にとどめる（数十頁なら通常は読み通せ、数百頁以上なら通常は読み通せない）。
判定と理由は計画か現在要約に一行残し、規模が変わったら見直す。

|水準|対象の例|確認の深さ|消費の規則|
|---|---|---|---|
|**短い文書**（一回の文脈で全体を読める）|論文、数十頁のノート、一章だけの講義|すべての証明を一段ずつ。決定的な証明はすべて独立確認。必要なら [proof-adversarial-review](../../proof-adversarial-review/SKILL.md) も既定で回す。出力は毎版全頁|この文書の下の規則は適用しなくてよい|
|**長い教材**（一回の文脈で全体を読めない）|数百頁〜数万頁の教科書・講義録|[数学確認の重点の段階](../../reading-book-math-review/SKILL.md#重点の段階)、[出力の機械検査先行](../../reading-book-output-review/SKILL.md#機械検査を先に)|下の規則すべて|

長い教材でも、部や章の終わり、決定的な定理は短い文書と同じ深さで読んでよい（範囲を区切って依頼する）。

## 何が消費を決めるか

モデルを呼ぶたびに、それまでの文脈全体が読み直される。消費はおおよそ「呼出回数 × その時点の文脈の大きさ」と
「出力量（思考を含む）」の和で決まり、出力は読み直しよりずっと高くつく。一度読み込んだ頁画像やファイル全体は
その後の全ての呼出で読み直され、新しい worker は起動のたびに基本文脈（指示・道具・接続の説明）を書き直す。
文脈を大きくした agent に細かい操作を何百回もさせる形、重い推論を同じ対象に重ねて掛ける形が最も高くつく。

## 能力の段階と思考量

役割ごとに**能力の段階**（上位・通常・軽量）と**思考量**（高・中・低）を対で決める。どの段階が実際にどのモデル・
どの推論設定かは教材ごとの設定ファイル（ホスト別）に書き、スキルや指示書にはモデル名を書かない。

|役割|段階|思考量|
|---|---|---|
|新しい証明（原著にない補完）の作成、その独立確認|上位|高|
|執筆（原著の議論の展開）、数学確認|通常|中|
|受領の整理、原著との照合、出力確認、キュー補充|通常|低|
|統括（判断が要るときだけ。既定はスクリプト）|軽量または通常|低|

統括が軽量段階のとき、統括は本文・証明・所見の中身を自分で読んで判定しない。worker は役割の段階を**明示して**起動し、
統括の段階を継承させない（継承すると worker も軽量になる。[起動の契約](../../research-router/references/subagent-invocation.md)）。
軽量段階の担当が自分で行った読取や判定は、確認・レビューとして数えない。消費を抑えるために段階を下げてよいのは
統括と機械的な作業（集計、hash、ビルドの実行）だけで、確認の段階は下げない。

## 規則（長い教材）

1. **統括はスクリプト。** 状態の集計、次の単位の選択、起動、待機、使用量の見張りは driver
   （[course_driver.py](../scripts/course_driver.py)）が行い、各周は会話を持たない一回きりの実行にする。回す前と回している間の確かめ方は [driver の試験と監査](driver-trial.md)。
   周で区切らず継続スレッドの LLM が統括する場合は、統括は**割り振りと受取りだけ**をする：本文・原著・長い報告を自分で読まず
   （読むのは単位ごとの worker）、状態は短い要約（状態 JSON の必要な欄、`status` 系の出力、進捗記録の最新数行）から読む。
   統括の文脈が育ったら（目安：worker の上限の 2 倍）、状態を書いて新しい文脈から再開する。
2. **一 worker 一単位。** worker は一節・一構成・一証明など一つの単位だけを担当し、呼出回数と文脈に上限を置く
   （目安：ツール呼出 30 回、文脈 8 万トークン）。超えそうなら途中結果と残りを返して終える。同じ worker を何単位も使い回さない。
   単位を閉じた worker は終わらせ、次の単位には packet と短い引継ぎだけを持たせた新しい worker を立てる。
   正本の唯一の編集者や公式ビルドの所有も、この交代で明示的に引き継ぐ（担当を長く生かして所有を保つことはしない）。
   一つの worker が単位を重ねると、呼出のたびに過去の単位の文脈まで読み直すので、消費は単位数の二乗で増える。
3. **最小の文脈で起動する。** worker には、担当スキルの要点を一枚にした役割カードと packet だけを渡し、
   必要な道具だけを許す。外部接続や全スキル一覧など、その単位で使わないものを積まない（ホストが対応する範囲で）。
4. **packet だけを渡す。** 対象行、引用ラベルの主張（証明は除く）、原著の該当頁の文字、hash を
   [make_packet.py](../scripts/make_packet.py) で切り出して渡す。章ファイル全体、進捗の全文、他の報告は読ませない。
5. **原著は文字で読む。** 原著は一度だけ [source_text_cache.py](../scripts/source_text_cache.py) で頁ごとの文字にし、
   キャッシュを全ての Git の外に置く。頁画像は、式・量化子・添字が文字では判読できない頁だけ、一単位で数頁まで。
6. **独立確認は一か所で一度。** 上位段階の独立確認は、制作側が依頼の packet を出し、確認側が
   [claim_packet.py](../scripts/claim_packet.py) で受付の印を置いてから起動する。印があれば他の担当は起動しない
   （[共通契約](../../course-authoring/references/production-handoff.md#独立確認の起動)）。
   既報の小さな穴の補修は通常段階の数学確認で再確認し、上位段階は原著にない決定的な証明だけに数単位まとめて使う。
7. **機械でできることはスクリプト。** 状態集計、hash、存在確認、packet 作成、出力検査、公式ビルドは LLM に読ませない。
   細かいシェル呼出を重ねず、一回の検査スクリプトで結果をまとめる。
8. **時間枠の予算で速さを決める。** ホストに時間枠ごとの上限があるときは、一周の消費を実測し、
   「一枠で回せる周数 ≒ 枠 × 使ってよい割合 ÷ 一周の消費」から周の間隔を決める（driver の `pacing`）。
   枠の大きさが公開されていなければ、ホストの表示する使用率の変化で一度較正する。
   周で区切らない継続スレッドでは、何単位かごとに使用量（[usage_report.py](../scripts/usage_report.py)）を見て、
   減る速さが「残りの割合 ÷ 枠のリセットまでの時間」を超えていたら、同時に動かす worker を減らし大きな文脈の作業を後に回す。
   止めるかどうかはユーザーが決める。
9. **確認は受領が追いつく速さで。** 未受領の返却が設定の上限を超えたら、新しい確認依頼より受領を先にする。
10. **待つときは長く一度に。** 目を覚ますたびに統括の文脈全体が読み直されるので、worker や他の担当を待つ間は、
    ホストが許す最長の待ち時間で完了通知を待つ（例：数分〜数十分）。短い sleep・短い timeout の待機・状態の確認を繰り返さない。
    待つ間に依存しない作業があればそれをし、なければ長く待つ。「止まらずに続ける」は仕事を続けることであり、
    見に行き続けることではない。キューが空で待つしかないときも、同じく長い待機を一回ずつにする。

消費の原因を調べるときは、ホストのセッション記録から（[usage_report.py](../scripts/usage_report.py)：時間枠の使用率・減る速さ・スレッド別とモデル別の内訳）役割別・段階別に呼出回数・文脈の大きさ・出力量を集計し、
画像の読込回数、同じ対象への重複した確認、待機の呼出（sleep・wait の回数と待ち時間）、worker ごとの呼出回数と最大の文脈を数える。推測で規則を足さない。
