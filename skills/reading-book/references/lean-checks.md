# 本文を助ける短時間の Lean 検査

本の制作では Lean を、気になる式・一補題・証明の一段階を確かめる補助チェッカーとして
選択的に使う。全巻の形式化や、もう一つの証明本文を維持する仕事に広げない。対象は
仮定の抜け、代表元独立性、添字・符号・量化子、修正した計算などから選ぶ。

## 既存スキルとの接続

検査用の小さな証明は [math-proof-worker](../../math-proof-worker/SKILL.md) の限定された
課題として扱う。作成者自身の利用は自己点検である。独立確認は通常の本制作の重要度に
応じて [math-verifier](../../math-verifier/SKILL.md) に依頼し、毎回別担当や査読書類一式を
必須にしない。read-only の検証担当に検査コードの新規作成や修正まで割り当てない。

[研究探索の Lean 規則](../../research-exploration/references/lean.md)は研究探索タスクの
完了条件であり、本の局所検査へそのまま持ち込まない。既に永続的な形式検証が明示的に
要求された対象は、その契約を維持する。ここでの簡易記録を `verified-formally` や
完了した formal review に転用しない。

## 小さく実行して本文へ戻す

1. **検査対象を一つに絞る。** 本文のラベル・対象版、疑問、仮定、確認する等式や推論を
   特定する。型・定義・量化範囲を照合し、本文で作るはずの構造を Lean 側で完成品として
   仮定しない。既存定理で結論だけを確認した場合は、本文の証明経路を検査したとしない。
2. **準備済みの環境を再利用する。** 使用する実体のバージョンと必要な import の準備を
   確認する。環境情報はセッションにつき一度記録して参照できる。局所検査ごとに Lake
   プロジェクト、依存ライブラリ、形式化カタログを新設しない。既存の固定環境の設定や
   依存版も変更しない。環境導入や大規模なライブラリ整備が必要なら、この検査は保留する。
3. **今回専用の一時ファイルで試す。** 教材 root の `cache/` 配下に一意な作業ディレクトリを
   作り、対象の名前付き宣言、型の表示、`#print axioms` を含める。準備済みの実行経路で
   実際に検査し、終了コードと対象に対応する出力を読む。既設の直接 Lean バイナリを
   使える場合は、依存取得を伴うプロジェクト操作を挟まず実行できる。必要な import が
   解決する経路とバージョンの対応は実行時に確認する。
4. **出力の意味を点検する。** 成功終了だけでなく、実際の宣言の型と公理出力を確認する。
   依存先を含む `sorryAx` があれば未完了。検査を通すために独自公理を追加せず、
   説明できない公理・追加仮定があれば成功としない。選択公理など本文で採用した前提は
   許容して使用を記録する。詳細な公理・実行証拠の解釈は既存の
   [形式検証の手順](../../research-management/references/formal-replay.md#evidence-and-axiom-policy)を
   参照するが、その永続カタログの作成をこの検査の前提にしない。
5. **結果を本文へ反映して片付ける。** 発見した数学的な不足や修正を本文と既存台帳へ
   戻す。短い結果記録を残してから、今回作った検査用コード・生成物・不要ログを削除できる。
   既存の原稿、確認記録、共有環境、依存ライブラリ、他の作業領域は削除しない。

記号を本文から貼り付けただけでは対応確認にならない。たとえば既成の数体系の法則を
呼ぶことと、その数体系を構成する演算が代表元によらないことは別の検査である。
有限個の値の計算はその値の検査であり、任意の値に対する証明とは区別する。

## 深追いしない

執筆の流れを保つため、初期の目安は一件5〜10分と少数回の局所修正にする。これは合否の
基準やユーザー指定の固定予算ではなく、続ける価値を判断する目安である。広い定義群や
新しい基盤の形式化が必要なら、疑問と止まった理由を記して本文へ戻る。Lean が通らない
だけでは数学の反証にならない。数学的疑義、本文との対応の不一致、実装・環境の不足を
区別する。実際の数学的な穴は未解決として扱い、検査の打切りで解決済みにしない。

繰り返し同じ検査を必要とする場合だけ、小さな検査コードの保持を検討する。常設化や
重い形式検証への移行は追加の制作判断であり、使い捨て検査の成功から自動的に始めない。

## 残すものと結果の呼び方

既存の台帳や節の記録に、次の内容を数行で残す。一検査ごとに別の台帳・報告書を作る
必要はない。

- 本文ラベル・対象版、検査した正確な命題または式、仮定、確認した範囲。
- 実行したコマンド、宣言名、環境情報への参照、終了状態と対象の公理出力。
- 本文との対応を誰が確認したか、分かったこと・修正・残る疑問。
- 一時ソースの保持／破棄。破棄した場合は、その記録だけから同じ検査を再実行できると
  約束しない。長い証明コードや大量のログの保存は通常要求しない。

「Lean 局所検査：この式について成功」「実装上の保留」「未実行」「対応未確認」など、
実態を明示する。本や定理全体の形式検証済みという状態に広げない。本文の主張・定義・
該当する推論が変われば、以前の結果を現行稿の検査済み扱いにせず、必要な箇所だけ再検査する。
ソースを破棄しても発見した誤り・未解決・修正の記録は残す。

検査コードと出力も原著・教材の派生物なので、[本の保存境界](storage.md)に従ってローカル
専用とする。外部の Lean サービスへ送らず、実教材を汎用スキルの例やテストにしない。
